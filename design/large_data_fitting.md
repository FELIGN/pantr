# Fitting a spline to large sampled data (3D images)

**Status:** design note for the C++ port. Nothing here is implemented.
**Date:** 2026-08-17.
**Scope:** the cost and the capability of fitting a tensor-product B-spline to a large
regular sample grid, the motivating case being a 3D MRI volume.
**Companions:** `design/bezier_extraction_api.md`, with which it shares one kernel, and
`design/user_functions_across_the_boundary.md`, for the case where the samples come from a
user-supplied function rather than from an image.

**Validated against:** pantr **0.7.0** (`main`, tag `v0.7.0`), 2026-08-19. Line numbers
below refer to that tree.

## The use case

A function known only by samples on a regular grid: a 3D image, typically `256³` to
`512³` voxels, stored as `uint16` or `int16`. Fit or approximate a tensor-product
B-spline to it, either at full resolution (interpolation, one coefficient per voxel) or
coarser (approximation, `n^d` coefficients for `N^d` samples with `n < N`).

## What is already right

The samples sit on a tensor-product grid, so the collocation matrix is a Kronecker
product `A = A_1 ⊗ A_2 ⊗ A_3` and the problem separates into three one-dimensional
problems, one per direction. The full `n^d × n^d` system is never formed. At `n = 128,
d = 3` that system would have `(2.1 × 10^6)²` entries, so this is not an optimization,
it is the difference between possible and impossible.

**pantr already does this.** `src/pantr/bspline/_bspline_interpolate.py:154`,
`_solve_kronecker`, solves direction by direction using `_flatten_along_axis`, and is
used by `interpolate_bspline` (`:406`), `_fit_from_tensor_product` (`:613`) and
`_l2_solve_components` (`:941`).

So the algorithmic structure needs no redesign. What follows is about the inner solve and
about a missing capability.

## The cost floor

Reference case, used throughout: MRI `512³` voxels as `float32`, cubic fit (`p = 3`) with
`128³` coefficients. Per direction, `m = 512` samples and `n = 128` basis functions.

Banded normal equations, direction by direction. All figures **derived**, not measured.

| direction | array shape | columns | flops |
|---|---|---|---|
| 1 | `(512, 512·512)` → `(128, 512·512)` | 262 144 | ≈ 1.6 × 10^9 |
| 2 | `(128, 512, 512)` → `(128, 128, 512)` | 65 536 | ≈ 4.0 × 10^8 |
| 3 | → `(128, 128, 128)` | 16 384 | ≈ 1.0 × 10^8 |
| **total** | | | **≈ 2.1 × 10^9** |

Memory traffic: 537 MB of input plus intermediates of 134 MB and 34 MB, so roughly
1.4 GB counting reads and writes. At around 50 GB/s that is **tens of milliseconds**, and
the operation is bandwidth-bound rather than compute-bound.

That is the number to hold onto. A `512³` fit is a tens-of-milliseconds operation. If it
takes seconds, the cause is the algorithm, not the hardware.

## How big do the arrays actually get

The question is worth answering with numbers, because the answer contains an asymmetry
that decides an API.

| `N` per axis | total `N`, `d = 3` | points `(N, d)` f64 | values `(N,)` f64 | values `(N,)` f32 |
|---|---|---|---|---|
| 128 | 2.1 × 10^6 | 50 MB | 17 MB | 8 MB |
| 256 | 1.7 × 10^7 | 403 MB | 134 MB | 67 MB |
| 512 | 1.3 × 10^8 | **3.2 GB** | 1.07 GB | 537 MB |
| 1024 | 1.1 × 10^9 | **25.8 GB** | 8.6 GB | 4.3 GB |

**The points array is `d` times the values array, and it is entirely avoidable.** For a
lattice, the sample positions are generated by `d` one-dimensional arrays totalling
`N_1 + N_2 + N_3` values: about 12 kB at `512³`, against 3.2 GB materialized. This is the
whole argument for the broadcasting contract in
`design/user_functions_across_the_boundary.md`, and it is a factor of 250 000, not an
ergonomic preference.

The values array is the real floor. It is the data, so it cannot be compressed away, and
`float32` versus `float64` is therefore the single largest memory lever available: for
12-to-16-bit image data, `float64` doubles the footprint for accuracy the data does not
contain.

Other arrays, for completeness: the 1D collocation matrices are `m × n` each, so about
2 MB at `512 × 512`, negligible. The `_solve_kronecker` intermediates shrink as each
direction reduces `N_d` to `n_d`, so peak memory is at the input end, not in the middle,
**provided** `n < N`. For interpolation (`n = N`) nothing shrinks and every intermediate is
full size.

### Peak memory, and where streaming helps

For the reference case (`512³` fit to `128³`, `float32`) peak is roughly the values array
plus the first intermediate, so 537 + 134 ≈ 670 MB, plus the four to six full-array copies
documented below, giving something in the region of 1.2 GB. At `1024³` the same estimate
is around 10 GB, which is no longer a laptop-sized problem.

Streaming helps, but asymmetrically, and it is worth knowing which direction is which:

- **Direction 1 streams trivially.** Its right-hand-side columns are independent, so the
  data can be processed in slabs of trailing indices: read `(N_1, k)`, solve, write
  `(n_1, k)`, discard. With the input memory-mapped, the input never needs to be resident.
- **Later directions do not.** Direction 2 needs all of `N_2` for each `(n_1, N_3)` index,
  so it needs direction 1's complete output before it starts, unless the problem is tiled
  in two directions at once.

So the achievable win is to move peak memory from the *input* down to the *first
intermediate*: 537 MB to 134 MB in the reference case, a factor of `N_1 / n_1`. That
closes the question of whether streaming is worth it: it is, and only the first direction
needs the machinery.

## The gap: the 1D solve discards the bandedness

`_bspline_interpolate.py:109-146`, `_solve_1d`, takes one of two paths:

- `m == n` (interpolation): `np.linalg.solve(mat, rhs)` on a **dense** matrix (`:132`).
- `m != n` (approximation, the fitting regime): **always** truncated SVD (`:136-145`).

The 1D collocation matrix has half-bandwidth `p`, so `p + 1 = 4` nonzeros per row out of
`n = 128` or `512` columns. Both paths ignore that.

The cost is **per right-hand-side column**, and there are `N^(d-1)` of them, so this is
where all the time goes:

| path | flops per column | at `n = 512, p = 3` | at `m = 512, n = 128, p = 3` |
|---|---|---|---|
| dense triangular solves (`np.linalg.solve`) | `≈ 2n²` | 5.2 × 10^5 | |
| dense SVD factors applied (`u.T`, then `vt.T`) | `≈ 2n(m + n)` | | 1.6 × 10^5 |
| banded Cholesky on the normal equations | `≈ 2m(p+1) + 4n(p+1)` | 8.2 × 10^3 | 6.1 × 10^3 |
| **ratio** | `O(n / p)` | **≈ 64×** | **≈ 27×** |

Two things worth being precise about, because the obvious reading is wrong in both cases.

**The cost is not the SVD.** Computing `svd(512 × 128)` is `O(m n²) ≈ 8 × 10^6` flops,
done once per direction, which is negligible. The cost is *applying* the dense factors
`u` and `vt` to every one of the 262 144 right-hand-side columns. Replacing the SVD with
a cheaper factorization of the same dense matrix would change almost nothing; the fix is
to stop storing and applying dense factors at all.

**Interpolation is relatively worse than approximation**, not better. The square path
pays `2n²` per column against a banded `4n(p+1)`, so its penalty is `n / (2(p+1))`. At
`n = 512, p = 3` that is 64×.

And the penalty **grows linearly with the number of coefficients per direction**. It is
27× at `n = 128` and 64× at `n = 512`; a `1024³` volume would be worse again. This is the
one inefficiency in the pipeline that gets worse as the data gets bigger.

### What the fitting path should be

For approximation with `m > n` the normal equations are the right choice here, not a QR
or SVD least-squares solve: the Gram matrix `AᵀA` is symmetric positive definite with
half-bandwidth `2p`, and the collocation matrix of a B-spline basis at reasonable nodes is
well conditioned, so the squaring of the condition number that normally argues against
normal equations is affordable. That last clause is a **claim that needs checking against
the node distribution actually used**, not a general licence: for nodes that cluster or
for a near-singular basis, `AᵀA` can be numerically singular where `A` is not, and the
rank-deficiency handling that the current SVD path provides would be lost.

So the honest recommendation is two paths, chosen explicitly rather than by a heuristic:
a banded Cholesky path for the well-conditioned case, and the existing dense
rank-revealing path retained as the fallback for when it is not. What must not survive is
the dense path being the *only* path, which is the situation today.

**Decided (2026-08-19): use Eigen's solvers.** Concretely `Eigen::SparseMatrix` with
`SimplicialLDLT`. Eigen has no dense *banded* solver, so the banded systems go through the
sparse side, which handles them correctly as a special case. It captures most of the 20x to 64x
above, because a sparse Cholesky does exploit the band.

> **Correction, 2026-08-21.** This paragraph originally justified the choice with "this is zero
> new dependency (Eigen is already required)", and that was false when written. Eigen was
> fetched only under `PANTR_BUILD_TESTS`, which `pyproject.toml` sets to `OFF`, so a
> `pip install` never cloned it and nothing in the shipped extension included one of its
> headers. The decision stands; the argument for it did not. Eigen became a real dependency of
> the product on 2026-08-21, taken deliberately by the change-of-basis port, whose builders need
> a dense solve and whose sibling `bezier` needs a truncated SVD pseudo-inverse. The measured
> cost is in `cmake/PantrDependencies.cmake`.

What it leaves on the table is the sparse machinery's index
indirection, which at bandwidth 7 and 262144 right-hand sides is not negligible but is not
an order of magnitude either. The escape, if a profile asks for it, is a hand-rolled banded
Cholesky of roughly 40 lines on the 1D path only: contained, and no API change.

### Two things about Eigen learned before its first use, and neither is about fitting

Eigen was surveyed in August 2026 for a different job, Gauss-Legendre nodes by Golub-Welsch
in the `quad` port. That port **declined it** and hand-rolled a Newton iteration instead, so
this note still holds Eigen's first real use. Two findings came out of that survey which are
facts about the library rather than about quadrature, and this is where whoever next reaches
for Eigen will look.

**`SelfAdjointEigenSolver::computeFromTridiagonal` is not scale invariant, and it fails
silently.** Its deflation test (`Eigen/src/Eigenvalues/SelfAdjointEigenSolver.h:509-513` in
5.0.1) compares `|e_i|` against `eps * sqrt(|d_i| + |d_{i+1}|)`. The left side is homogeneous
of degree 1 in the matrix scale and the right side of degree one half, so scaling the matrix
down loosens the criterion without bound. Measured on the Legendre Jacobi matrix scaled by
`1e-30`, which is 278 decades above `DBL_MIN` so no underflow is involved: **relative node
error of 150%, with `info()` reporting `Success`**. The dense `compute()` path does not
suffer it, because it normalizes by the largest coefficient first and multiplies back
(`:436-446`); the tridiagonal entry point carries the maintainer's own `TODO` about the
missing scaling at `:457`. The constant in that test was tuned empirically: the commit that
introduced this form was followed two weeks later by one whose message records that the
theoretically correct value broke internal tests and was reverted. So a caller who reaches
for the tridiagonal path, which is the natural one for a matrix that is already tridiagonal,
must add the normalization itself.

**`sum(w) = 2` is a vacuous health check on that path.** The obvious cheap certificate for a
Golub-Welsch weight vector holds **even when the iteration does not converge at all**,
because the weights are read from the first row of an accumulated product of Givens
rotations, which stays a unit vector however badly the sweep did. Measured: with the
iteration budget forced to zero, `info()` reports `NoConvergence`, the diagonal is
untouched, and the weight sum is still exactly 2. Whatever Eigen path this note's solvers
end up on, **`info()` must be propagated**; there is no numerical signal that substitutes
for it.

Neither finding touches `SparseMatrix` or `SimplicialLDLT`, which is what the decision above
actually selects. They are recorded because both were expensive to find and neither is
visible from the documentation.

## Full-array copies

`_flatten_along_axis` (`src/pantr/_array_utils.py:37-58`) does `np.moveaxis` followed by
`np.ascontiguousarray`. For direction 0 the moveaxis is a no-op and the reshape is a view,
so it is free. For every other direction it **copies the whole array**.

Combined with `result = rhs.copy()` at `_bspline_interpolate.py:178` and
`np.array(result, dtype=rhs.dtype)` at `:183`, a 3D solve makes on the order of four to
six full-array copies of decreasing size. The largest are at the input end, where the
array is 537 MB.

Estimated copy traffic is of the same order as the useful traffic, so copies roughly
double the memory cost of an operation that is already bandwidth-bound. In C++ this is
avoidable: the per-direction kernel can read strided input directly rather than
materializing a contiguous transpose, at the cost of worse locality, or the two largest
copies can be eliminated by writing into a caller-provided buffer and alternating between
two buffers across directions.

## Precision

`float32` is supported throughout (the signatures are `np.float32 | np.float64`), which
matters: MRI is 12 to 16 bit integer data, and forcing `float64` doubles a 537 MB volume
to 1.07 GB for no accuracy that the data contains.

One rule to state explicitly in the port: **accumulate in `float64` even when the data is
`float32`.** Forming a Gram entry sums `m = 512` products; in `float32` the relative error
grows like `sqrt(m) · eps_32 ≈ 22 · 6 × 10^-8 ≈ 1.3 × 10^-6`. That is acceptable against
16-bit data, but it is close enough to matter that it should be a decision rather than an
accident, and mixed precision costs nothing here because the accumulator is a scalar.

## The capability gap: no regularization

Verified by search: there is no penalty, smoothing, ridge or Tikhonov term anywhere in
`_bspline_interpolate.py`. `fit_bspline` (`:497`) takes only `tol`, which is the SVD
truncation tolerance.

For image data this is not a detail. MRI is noisy, and an unpenalized fit chases the
noise. Truncated SVD is **not** a substitute: it handles rank deficiency, and while it
does regularize in a loose sense, it cannot control the magnitude of derivatives, which
is what smoothing means here.

### Why a penalty breaks the separability

`AᵀA` is a Kronecker **product**, `G_1 ⊗ G_2 ⊗ G_3`. A second-derivative smoothness
penalty is a Kronecker **sum**:

```
P = P_1 ⊗ I ⊗ I  +  I ⊗ P_2 ⊗ I  +  I ⊗ I ⊗ P_3
```

A Kronecker sum does not factor into a sequence of per-direction solves. So
`AᵀA + λP` cannot be handled by `_solve_kronecker` at all. This is not missing code, it
is the method not applying.

Three ways out:

1. **Conjugate gradients with the Kronecker matvec.** Always applies. Keeps
   `O(d · p · N)` per iteration and `O(N)` memory, and the matvec is the *same primitive*
   the direct solve already uses. Precondition with the unpenalized separable solve,
   which is a natural and strong preconditioner. Being iterative, a sweep over `λ` is
   cheap.
2. **A generalized eigendecomposition per direction**, in the spirit of GLAM (Currie,
   Durbán and Eilers, *Generalized linear array models with applications to
   multidimensional smoothing*, JRSS-B, 2006), which turns the solve into a pointwise
   division in a transformed basis. **This works under conditions** on the simultaneous
   diagonalizability of the per-direction pencils, and those conditions must be verified
   before relying on it rather than assumed.
3. Approximate with a separable penalty and accept the modelling error.

Recommendation: option 1. It is robust, it reuses machinery that already exists, and it
requires no theorem to be checked first. Option 2 is worth revisiting if profiling shows
CG iteration counts to be the bottleneck, which would be an argument grounded in
measurement rather than in elegance.

## A cliff worth documenting

`fit_bspline` accepts scattered nodes as well as tensor-product ones, and the scattered
path (`_fit_from_scattered`, `:620`, via `_build_nd_collocation_matrix`, `:671`) builds
the **full nD collocation matrix** and solves by SVD. For a `512³` volume that matrix
would have `1.3 × 10^8 × 2.1 × 10^6` entries. It is not merely slow, it cannot be
allocated.

The tensor-product path is taken automatically for lattice input, so nothing is broken
today. But the two paths differ in feasibility by many orders of magnitude behind one
function name, and the docstring should say so. In the port this is an argument for the
node layout being visible in the type rather than sniffed from the argument
(`_is_scattered_nodes`, `:290`).

## CUDA

This is the best-supported candidate for a GPU of anything discussed so far, and it still
does not pay on its own.

Transferring 537 MB over PCIe at around 20 GB/s costs 27 ms each way, so 54 ms round
trip, against a host computation whose floor is roughly 20 to 30 ms. **The transfer alone
exceeds the entire computation.**

Two exceptions, and the second is a real workflow:

- The volume already lives on the device, because it came from an imaging pipeline that
  runs there. Then only the compute matters, and the GPU's bandwidth advantage applies
  directly to a bandwidth-bound kernel.
- **A sweep over the regularization parameter `λ`.** Upload once, solve many times. With
  the iterative path above, this amortizes the transfer over as many solves as the sweep
  has points, and it is the first case in this design discussion where a GPU is clearly
  the right tool.

## One primitive serves three operations

The kernel underneath all of this is: *apply a banded 1D operator along axis `d` of an nD
array, for every combination of the remaining indices.*

That is the same primitive as Bézier extraction
(`_bspline_to_beziers.py:_apply_bezier_extraction_1d_core`) and as nD spline evaluation by
sum factorization. Three operations, one kernel.

In the port it should be a first-class, well-optimized primitive with its own benchmarks,
not three separate loops that happen to look alike. It is also the natural place for the
blocking discussed in `design/bezier_extraction_api.md`, and the natural unit for the
`float32` / `float64` accumulation rule above.

## Epistemic status

- **Verified by reading the code**, at the lines cited: that `_solve_kronecker` exploits
  separability (`:154-183`); that `_solve_1d` uses a dense solve or a dense SVD and never
  a banded factorization (`:109-146`); that `_flatten_along_axis` copies for every
  non-leading axis (`_array_utils.py:57-58`); that no regularization term exists; that
  the scattered path builds a full nD matrix (`:620`, `:671`).
- **Derived**, not measured: every flop count, byte count and ratio in this note,
  including the `O(n/p)` penalty and the 27× / 64× figures. Bandwidth and PCIe rates are
  order-of-magnitude figures for commodity hardware, not measurements of a specific
  machine.
- **A claim needing a check, flagged in place:** that normal equations are numerically
  acceptable here. It depends on the conditioning of the collocation matrix at the node
  distribution actually used, and it is stated conditionally for that reason.
- **Not investigated:** whether the observed cost on real volumes matches this model. No
  profile was run. The model predicts that time is dominated by applying dense factors
  across right-hand-side columns, and that is the first thing a profile should confirm or
  refute.

- **Surveyed 2026-08-20, and it is about Eigen rather than about fitting.** The two findings
  in "Two things about Eigen learned before its first use" were measured while evaluating
  Eigen for a job this note does not cover, and that job then declined it. The dimensional
  inconsistency of the deflation test and the `TODO` about the missing scaling were verified
  by reading Eigen 5.0.1 at the pinned SHA; the 150% relative node error at scale `1e-30`
  and the weight sum surviving a forced non-convergence were measured by the survey and are
  taken on its report rather than reproduced here. Neither touches `SparseMatrix` or
  `SimplicialLDLT`, which is what this note actually selects, so the decision above stands
  unchanged.

## Open questions

1. Which regimes must be supported: interpolation at full resolution, coarse
   approximation, or both? They want different default solvers, and the answer determines
   whether the banded Cholesky path or the interpolation path is written first.
2. Is a smoothing penalty in scope for pantr, or does it belong to the consumer? It is
   the thing the MRI case actually needs, but it is also the first piece of *statistics*
   in a geometry library. Worth deciding deliberately.
3. If yes to 2: is `λ` a scalar, per direction, or chosen automatically (generalized
   cross-validation, AIC)? Automatic selection is a sweep, which is what makes the GPU
   case above real, and it is considerably more scope than a fixed `λ`.
4. Should the node layout (tensor-product versus scattered) be a type distinction rather
   than sniffed at runtime, given that the two paths differ in feasibility rather than
   only in speed?
5. ~~Does the input need a streaming path?~~ **Answered above.** Yes, and only direction 1
   needs it: peak memory drops from the input to the first intermediate, a factor of
   `N_1 / n_1`. What remains open is whether the input is accepted as a memory-map or as an
   in-memory array, which is an API question rather than an algorithmic one.
6. `design/adaptive_thb_approximation.md` needs the residual, not the values, on the second
   and later iterations. Whether the residual replaces the values array in place (halving
   peak memory, destroying the input) or is allocated alongside it (doubling peak) is a
   decision that belongs with this note's memory model rather than with the adaptive one.
